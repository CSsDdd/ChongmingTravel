## 一、项目背景情况

项目当前是一个本地可运行的微信小程序 Demo，面向崇明户外打卡点发现、个人路线组织和日程安排。数据仍来自 Sample Seed 与微信本地 Storage，不包含真实服务端、真实审核后台或跨设备媒体存储。

当前继续保持以下边界：

- 页面通过 Repository 访问数据，不直接操作底层 Storage。
- Checkpoint 与 Route 的公开内容、草稿和稳定身份分开保存。
- Schedule 通过 `targetRef = { type, id, version }` 引用打卡点或个人路线。
- 点赞、收藏等用户行为使用独立交互记录；公开顶层对象仍暂时保留聚合计数和旧的 `likedUserIds` 兼容字段。
- 评论计划作为独立辅助结构，不直接挂在 Checkpoint 或 Route 顶层对象下。

当前仍属于本地模拟系统。审核通过、分享次数、浏览量和用户交互只证明本地业务链路可演示，不代表真实权限隔离、并发计数和跨设备同步已经成立。

### 2. 当前核心数据结构

#### Checkpoint

Checkpoint 当前采用三层结构：

- `Checkpoint`：稳定身份、所有者、最新版本指针、当前公开版本指针，以及点赞/收藏/分享/浏览聚合字段。
- `CheckpointVersion`：某一公开版本的标题、短描述、图片、位置、标签和发布时间。
- `CheckpointDraft`：当前用户可编辑草稿及审核状态。

Checkpoint 已提供公开 DTO 接口，页面可以通过 DTO 获取隔离后的展示数据，而不必直接持有 Repository 内部对象引用。

#### Route

Route 当前同样采用三层结构：

- `Route`：稳定身份、所有者、来源路线引用、版本指针、创建时间和公开交互聚合字段。
- `RouteVersion`：已发布的不可变路线内容与发布时间。
- `RouteDraft`：当前工作区草稿、审核状态、创建时间和更新时间。

Route 内容包括：

- `title`
- `description`
- `note`
- `coverImageId`
- `tagIds`
- 有序 `stops`

每个 Stop 当前包括：

- `checkpointId`
- `checkpointVersion`
- `note`
- `trafficToNext`

复制公开 Route 的语义已经确定为“创建新的 Route 身份”，并通过 `sourceRouteRef = { routeId, version }` 记录来源，而不是把不同用户的分支塞进原 Route 的后续版本。

#### Schedule

Schedule 当前支持两类目标：

- `CHECKPOINT`
- `PERSONAL_ROUTE`

当前代码只保存 `targetRef = { type, id, version }`，尚未保存确认时的内容快照。因此，“已完成或已确认 Schedule 不受来源内容后续变化影响”的冻结语义目前还没有完整落实。

### 3. Route 草稿与发布闭环

已完成的 Route Repository 能力包括：

- 创建新 Route 草稿。
- 更新已有草稿。
- 查询当前用户草稿。
- 提交审核、撤回审核和删除草稿。
- 模拟审核通过后发布 `RouteVersion`，并让工作区草稿前进到下一版本。
- 查询公开 Route、指定 RouteVersion 和公开 DTO。
- 从公开 RouteVersion 派生新的 Route 身份及 Version 1 草稿。
- 维护公开 Route 的浏览量与分享量。

Route Editor 当前已形成基本编辑闭环：

- 新建和编辑复用同一页面及 `update` 保存入口。
- 可以有序管理 Stops。
- 支持在指定位置插入 Stop、删除 Stop、拖拽排序及拖拽预览。
- Stop 展示 Checkpoint 概览图，并允许填写 Stop Note。
- 支持选择节点间交通方式。
- 保存和提交审核按钮位于页面下方。
- 当前审核仍为客户端本地模拟审核。

Editor 首页已支持 Checkpoint 草稿与 Route 草稿页签；“复制已有 Route”入口仍是占位逻辑，尚未接入 Route Picker。

### 6. 当前未提交的 Route → Schedule 集成

当前工作区正在完成以下链路：

1. Route Detail 点击“导入安排”。
2. 如果是自己的公开 Route，优先查找同 Route 的工作区草稿。
3. 如果没有可用个人草稿，或来源属于其他用户，则从公开版本复制并创建新的个人 Route 草稿。
4. 页面通过 URL 查询参数传递 `targetType`、`targetId` 和 `targetVersion`。
5. Schedule Editor 解析这些参数，以 `PERSONAL_ROUTE` 作为预选且锁定的目标创建 Schedule。
6. Schedule 列表开始按目标类型解析 Checkpoint 或 Route 的标题。

新的 Schedule Target Picker 已创建并注册到 `app.json`。它与 Route Editor 使用的 Checkpoint Picker 分开，原因是二者的数据边界不同。

Schedule Target Picker 当前允许看到：

- 所有公开 Checkpoint。
- 当前用户自己的 Checkpoint Draft。
- 当前用户自己的 Route Draft。

它故意不直接列出所有公开 Route。公开 Route 应先经过 Route Detail 复制到个人工作区，再导入 Schedule。Repository 会把不同来源压平成统一的 Picker DTO；`source` 只用于界面显示“公开/我的草稿”，不会写入 Schedule。

Picker 当前支持：

- 文本搜索。
- “全部 / 打卡点 / 路线”筛选。
- 图片或占位显示。
- 通过 EventChannel 把目标引用返回 Schedule Editor。
- “公开 / 我的草稿”徽标；其 flex 居中、单位错误和字体视觉偏移已修复。

Checkpoint Detail 中多余的“加入路线”按钮已经从当前工作区删除，因为 Route Editor 负责通过 Checkpoint Picker 组织路线，详情页不需要重复入口。

### 7. 当前已知问题

#### Route 目标版本解析已修复

`pages/schedule/editor/schedule-editor.js` 与 `pages/schedule/schedule.js` 在解析 `PERSONAL_ROUTE` 时，现已检查同 ID 草稿的版本是否等于 `targetRef.version`。

Checkpoint 的对应逻辑已经检查版本一致性：

```js
if (draft && draft.version === targetRef.version) return draft
return checkpointRepository.findVersion(targetRef.id, targetRef.version)
```

Route 与 Checkpoint 现采用相同规则：只有版本匹配时才返回草稿，否则查询引用指定的公开版本，避免旧版本 Schedule 错误显示为最新草稿内容。

#### Schedule 冻结语义尚未完成

当前 Schedule 仅保留目标引用，没有冻结快照。用户已经提出：已完成的 Schedule 应当冻结；公开 Route 已有安排时，继续修改工作区内容可以提示确认，但不希望每次创建 Schedule 都机械生成新的冻结 RouteVersion。具体实现仍需结合 `target.snapshot` 或等价快照结构进一步讨论。

#### 尚未完成首轮运行验证

本轮 Route → Schedule、目标选择器及徽标样式修改只完成了代码与静态检查，尚未在微信开发者工具中完成完整编译和交互测试。
