# 崇明青少年户外探索平台进度总结

## 一、项目背景情况

### 项目定位

建设一个以用户生成内容（UGC）为主的崇明户外探索平台，重点服务青少年及其家庭。平台以具体、可定位、具有直观吸引力的“打卡点”为核心内容单位，帮助用户发现打卡点、组织路线、安排时间并寻找同行者，将兴趣转化为实际短途出行。

### 核心差异

1. UGC 围绕具体打卡点组织，而非泛化景点或一般图文贴文。
2. 打卡点可直接进入路线、安排和同行邀约，形成从内容发现到出行行动的连续流程。

### 核心使用场景

- 出行规划：带着明确出行意愿筛选打卡点、组织路线、创建安排和邀请同行者。
- 碎片时间浏览：在通勤、候车等空闲时间浏览即时发现卡片，积累备选点并进一步形成路线或安排。

## 二、项目现状

### 当前材料

- `要求.md`：当前项目需求与业务数据骨架。
- `要求-初稿.md`：最初需求草稿，仅作历史参考。
- `待确认事项.md`：内部访谈提纲，先确认任务范围，再按需要讨论政策和隐私。
- 当前尚无 Android 工程或其他代码。

### 交付边界

当前目标为可交互 Android 演示原型：

- 使用本地持久化数据和模拟用户；
- 真实实现核心业务状态变化；
- 暂不实现真实账户、服务端、多用户实时通信、自动审核和真实地图服务；
- 未来可考虑接入地图或导航 App，但不属于当前原型必须功能；
- 内容治理、实名、隐私细则和后续运营责任仍待与区里确认。

### 四类主要数据对象

#### User

- 稳定 ID；
- 个人档案；
- 默认隐私配置；
- 实名身份信息与认证状态分离；
- 账号状态和创建时间。

#### Checkpoint

- ID、版本、创建者；
- 经纬度、位置名称、坐标体系；
- 标题、一句话正文、一张图片、标签；
- 发布或审核状态、创建时间。

定位用于附近查询、相近内容聚合和未来导航。平台不保存固定的大地点归属。

#### Route

- ID、版本、创建者、标题、说明和标签；
- 有序 `stops` 数组；
- 每个节点保存 `checkpointId` 和 `travelModeFromPrevious`，第一站的交通方式为空；
- 不保存导航服务生成的具体道路路径。

#### Schedule

- 可见状态：`private | public | restricted`，其中 `restricted` 的范围待确认；
- 所属用户、开始时间、结束时间；
- 目标类型为打卡点或路线；
- 保存来源 ID、版本和冻结快照；
- 计划状态和招募状态分离；
- `sharedNote` 保存集合点等共同信息，接受邀请时复制；
- `privateNote` 仅由本人维护，不随邀请复制；
- 可选保存来源邀请 ID。

### 快照与版本原则

- `Checkpoint` 和 `Route` 预留版本号。
- 当前原型不实现完整历史版本服务。
- 创建或确认安排时，`Schedule.target` 保存必要快照，保证来源内容后续修改不会改变已确认安排。
- 未来正式服务端可扩展为不可变历史版本，由安排引用确定版本。

### 核心功能闭环

```text
发布并发现打卡点
→ 将多个打卡点组织为路线
→ 围绕打卡点或路线创建安排
→ 在打卡点页面发现具有共同意向的用户
→ 通过消息沟通并发送结构化邀请
→ 对方接受后复制共同安排到个人日历
```

同行候选暂定包括：

- 直接为当前打卡点创建公开招募安排的用户；
- 安排的路线包含当前打卡点的用户，标注“计划路线包含此打卡点”。

聊天、邀请、用户关系等属于辅助数据，不改变四类主要对象。原型至少需要轻量的邀请状态及本地会话数据，以支撑完整演示。

### 尚待确认

#### 任务范围

- Android 原型、安装包、源代码、需求与设计说明、演示材料的具体交付要求；
- 示例打卡点、路线和模拟用户的数量及素材来源；
- 验收侧重点和明确标准；
- 正式上线、持续开发和运营是否不属于本阶段责任。

#### 政策与隐私

- 本阶段是否需要形成未来正式上线的隐私、身份认证和治理方案；
- `restricted` 的具体可见对象；
- 未成年人默认可见范围和监护人确认要求；
- 哪些用户可以查看同行意向、发送消息和邀请；
- 审核、举报、身份认证及第三方服务的责任边界。

## 三、项目计划情况

### 开发前第一项决定

确定 Android 技术栈和本地数据方案。尚未正式选型；建议评估 Kotlin、Jetpack Compose 与 Room，但选型不是当前已确认事实。

### 建议实施顺序

1. 创建 Android 工程，建立 UI、业务逻辑和本地数据访问的基本分层。
2. 实现四类主要数据模型，以及轻量的邀请、会话和消息模型。
3. 准备示例打卡点、路线、安排和 Bot 用户数据。
4. 实现打卡点浏览及打卡点发布，本地持久化新增内容。
5. 实现路线编辑，保存有序打卡点链和逐段交通方式。
6. 实现个人日历与安排创建，保存目标快照、可见性和两类备注。
7. 实现打卡点同行候选查询，包括直接安排和路线包含两种情况。
8. 实现本地消息、结构化邀请及接受后复制安排的完整链路。
9. 补充演示所需的身份、审核和隐私模拟状态。
10. 完成视觉统一、异常状态、持久化验证和演示流程测试。

### 最小验收链路

- 新建打卡点后可在重新进入页面后看到该卡片；
- 可选择多个打卡点组成并保存路线；
- 可围绕打卡点或路线创建安排并在日历显示；
- 打卡点页面可发现直接安排或路线包含该点的模拟同行者；
- 可发送并接受结构化邀请；
- 接受后生成独立安排，复制快照和 `sharedNote`，不复制 `privateNote`；
- 修改来源路线不会改变已经确认的安排快照。

### 近期下一步

1. 完成与区里的任务范围确认；政策部分按对方答复决定是否展开。
2. 确定 Android 技术栈和工程结构。
3. 建立项目骨架与第一批本地示例数据。
