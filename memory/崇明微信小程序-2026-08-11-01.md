# 崇明微信小程序进度记录

## 一、项目背景情况

当前目标是完成一个本地可运行的微信小程序 Demo，主要功能包括崇明户外打卡点发现、用户资料、用户路线与日程安排。当前不接入正式服务端：用户、Checkpoint 和 Schedule 等数据通过 Sample 数据与微信本地 Storage 模拟，同时保留 Model、Repository、Page、Component 与 WXML/WXSS 的分层，以便以后替换真实数据源。

当前 Schedule 使用统一目标引用：

```js
targetRef: {
  type,
  id,
  version,
}
```

`CHECKPOINT` 通过 Checkpoint Repository 解析；`PERSONAL_ROUTE` 计划在路线结构和用户 Workspace Repository 完成后接入。

### 2. Schedule 数据层

- 已建立 Schedule 工厂及字段、状态组合验证。
- 已建立使用微信本地 Storage 的 Schedule Repository。
- Repository 已提供 `findById()`、`findByOwnerAndRange()`、`create()` 和 `update()`。
- Schedule ID 通过 `nextScheduleSequence` 生成连续的本地演示 ID。
- 时间范围查询使用半开区间重叠判断，支持跨日安排。
- 生命周期通过计划状态表达，当前没有仅为补齐 CRUD 而增加物理删除接口。

### 3. Schedule 编辑页

- 已建立共用的新建/编辑页面，并在 `app.json` 中注册。
- 已支持 Sample Checkpoint、开始和结束时间、可见性、招募状态、计划状态、共享备注和私人备注。
- 新建模式调用 Repository 的 `create()`；编辑模式调用 `update()`。
- 编辑已有 Schedule 时会验证当前用户是否为 `ownerUserId`。
- 已有目标在编辑模式下暂时只读。
- 已加入未保存退出提醒。
- 当前真正接入的目标类型仍只有 `CHECKPOINT`；`PERSONAL_ROUTE` 尚未实现。

### 4. Schedule 日期详情页

- 已通过 `createLocalDayRange()` 和 `findByOwnerAndRange()` 查询选中日期内的安排。
- 已建立异步 `toScheduleCard()` 展示映射：格式化起止时间、解析 Checkpoint 标题、翻译计划/招募状态，并生成卡片需要的字段。
- 私人备注只向 Schedule 所有者提供；单条卡片的 `canEdit` 仍根据访问者与 `schedule.ownerUserId` 的关系计算。
- Page 层已区分：
  - `currentUser`：当前访问页面的用户；
  - `ownerUserId`：当前日程表属于谁；
  - `canManageSchedules`：当前访问者是否可以管理该日程表。
- 日程列表和日历标记已经改为使用 `ownerUserId` 查询，不再直接使用 `currentUser.id` 作为查询主语。
- 当前阶段 `ownerUserId` 仍默认取当前登录用户 ID，因此视觉和数据结果暂时与原有“只看自己”模式一致。
- 尚未开放通过 URL 查看其他用户的日程表；在实现该能力前，需要增加按可见性过滤的 Repository 查询，避免返回其他用户的私人 Schedule。

### 5. Schedule 日历组件

- 非本月日期使用淡灰色显示。
- 点击非本月日期会切换月份并触发日期变化，Page 随后重新加载日程列表和日历标记。
- Profile 页面已接入相同的日历标记数据流。

## 三、当前明确问题

### 1. 新建入口被错误拦截

当前安排卡片和“添加安排”按钮共用 `goToScheduleEditor(e)`。添加按钮没有 `data-schedule-id`，函数因此找不到 Schedule，并被“只能编辑自己的安排”的判断拦截。

用户认为现有编辑函数的职责较清晰，暂时不希望修改它。后续应单独讨论最小修复，优先考虑：保留现有编辑函数，给添加按钮建立独立的新建入口，并由 Page 层的 `canManageSchedules` 控制是否允许创建。

### 2. Page 所有者语义尚未完整使用

虽然 `ownerUserId` 和 `canManageSchedules` 已进入 Page 数据，但 WXML 尚未使用 `canManageSchedules` 控制添加按钮，Page 也尚未从页面参数加载其他用户作为所有者。

在允许查看其他用户之前，必须先定义并实现可见性查询规则。不能直接把任意 URL 中的 `ownerUserId` 交给现有 `findByOwnerAndRange()`，因为现有接口会返回该用户时间范围内的全部 Schedule。

## 五、对话与分支交接建议

- 上下文压缩不会导致必须重开对话；只要进度文件和当前代码状态准确，当前对话可以继续。
- 推荐按“一个清晰功能目标或一个 PR”划分对话，而不是机械要求每个 Git 分支只能对应一个对话。
- 当一个分支承担一个独立功能时，一个分支对应一个对话通常最清晰，例如 `feat.schedule-editor`、`feat.schedule-visibility`。
- 小修复、同一功能的连续调整不必频繁开新对话，否则容易把尚未提交的依赖拆散。
- 最稳妥的切换时机是：当前功能已验证并提交，然后创建下一分支，同时开启新对话，并让新对话先读取最新进度文件与 `git status`。
